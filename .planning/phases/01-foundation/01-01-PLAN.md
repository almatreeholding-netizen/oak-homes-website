## Executor shell contract — read before running any `<verify>` block

**This machine's executor session shell is Windows PowerShell 5.1.** It is not POSIX. `&&` is a
parse error, `$(...)` is rejected, and `cmp`, `wc`, `test`, `find`, `grep`, and `for f in ...` do
not exist as commands. A Bash-syntax verify block does not *fail* there — it fails to *parse*,
which reads as noise and invites the executor to skip verification silently. That is the failure
this contract removes.

**Therefore every `<automated>` block in plans 01-01 through 01-05 is exactly one command:**

```
node scripts/verify/checks.mjs <check-id>
```

`scripts/verify/checks.mjs` is a dependency-free Node ESM CLI created in Task 2 of this plan and
extended by one named check per task thereafter. Node is the one runtime this project already
requires (v24.19.0 on this machine), and `node <file> <arg>` parses identically under PowerShell,
cmd.exe, and bash — so no shell contract is inherited by anything downstream.

**Rules every check must follow:**

- Exit code 0 means PASS and the process prints `PASS <check-id>`. Any failure prints
  `FAIL <check-id>: <reason>` on stderr and exits non-zero.
- Node built-ins only — `node:fs`, `node:path`, `node:child_process`, `node:url`. The single
  exception is `sharp`, used by the `photos-resized` check in plan 01-03, by which point it is
  an installed devDependency.
- Never shell out to `grep`, `find`, `wc`, `cmp`, or `test`. Read files with `node:fs` and count
  occurrences with a regex or `String.prototype.split`.
- Subprocesses use `spawnSync` with an explicit argv array and no shell string. For npm, use
  `spawnSync(process.platform === 'win32' ? 'npm.cmd' : 'npm', ['run', 'build'], { stdio: 'inherit' })`
  — `npm` on Windows is a `.cmd` shim that `spawnSync` cannot launch without the extension.
  For git, `spawnSync('git', [...], { encoding: 'utf8' })`.
- A check that cannot run its assertion — missing file, missing prerequisite, unreadable input —
  **fails loudly**. It must never print PASS on a skipped assertion. A check that passes without
  proving anything is worse than no check, because it reads as coverage.
- Checks take no arguments beyond the check id and read nothing from the environment, so a check
  behaves the same for the executor, the checker, and a human re-running it a month later.
</shell_contract>
