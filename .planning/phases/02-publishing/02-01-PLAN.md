<objective>
Prove the entire publishing pipe end to end on one thin path, then stop: a commit reaches
GitHub, Netlify builds and atomically deploys it, `/admin` loads a real form-based panel,
GitHub sign-in works through Netlify's OAuth broker, and one real edit made in that panel
lands on the live site. This is the phase's tracer — production-quality, not a prototype.
Every artifact it creates is the final artifact; the only thing deliberately narrow is the
number of collections wired (Homes only — Learn Posts and Site Settings expand out from this
proven slice in 02-02).

Phase goal, verbatim from ROADMAP.md: *"The assistant can add a home through a form and watch
it appear on the live site about two minutes later, without touching code or asking anyone."*

Two setup steps here are browser-only and were re-verified as unscriptable in this exact
environment, not merely inherited from research: `command -v netlify` and `command -v gh`
both exit 1. Creating/linking a Netlify site and registering a GitHub OAuth App therefore run
as human-in-the-loop tasks (RESEARCH Pitfall 5), and D-21 makes the Netlify branch an explicit
live check rather than an assumption — the owner does not know whether a site is already
linked to this repo.

Purpose: everything in Phase 2 and every future content change depends on this pipe. Proving
it on one path now costs one commit; discovering it broken after three collections and a
cheat-sheet ship costs the phase.
Output: `netlify.toml`, `public/admin/index.html`, `public/admin/config.yml` (Homes
collection), a new `cms-tracer-config` check id, a live site building on every push, and a
working `/admin` login.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| assistant browser → Sveltia CMS → GitHub API | Authored content and an OAuth token cross from an untrusted browser into the repository. |
| GitHub OAuth App ↔ Netlify OAuth broker ↔ browser | Identity and a scoped access token cross three parties, none of them this repo. |
| GitHub repo → Netlify build → live HTML | CMS-authored content becomes publicly rendered HTML. |
| public internet → `/admin` and `/admin/config.yml` | Both are static files served to anyone; only *writes* are gated. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Information Disclosure | GitHub OAuth App Client Secret | high | mitigate | Secret is entered only in Netlify's Access & security → OAuth form (Task 2 step 4). `public/admin/config.yml`'s backend block carries only name/repo/branch — no secret and no broker override. `cms-tracer-config` asserts no file under `public/admin/` contains a secret- or token-shaped value; Task 2 acceptance greps `public/admin` for secret keys. |
| T-02-02 | Information Disclosure | `public/admin/config.yml` served publicly at `/admin/config.yml` | low | accept | The file discloses the repo owner/name and content paths to anyone who fetches it. A repository name is not a credential: the repo is private and GitHub enforces access independently, and the admin shell carries a robots noindex meta to keep it out of search results. Documented rather than mitigated because the only mitigation (moving config behind a server) would require Netlify Functions, which this phase opts out of. |
| T-02-06 | Spoofing | `/admin` sign-in by a non-collaborator GitHub user | medium | mitigate | Access control is delegated to GitHub repository collaborator permissions (RESEARCH Security Domain V4): Sveltia writes through the GitHub API as the signed-in user, so a non-collaborator cannot commit. No application-level role check is added — building one would duplicate GitHub's. Flagged as an untested assumption above. |
| T-02-SC | Tampering | Sveltia CMS loaded from the unpkg CDN | high | mitigate | An unpinned CDN URL serves whatever unpkg considers newest, so a compromised or hostile release would execute in the admin panel with access to the assistant's GitHub OAuth token — full write access to the repo and therefore to the live site. Task 1 pins the URL to an exact published version resolved at execution time, and `cms-tracer-config` fails if the URL lacks a version specifier.
