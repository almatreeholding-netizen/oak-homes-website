<objective>
Expand out from the proven tracer slice: wire the two remaining collections so the assistant
can publish a Learn post (ADMIN-04) and change site settings (ADMIN-05) through the same panel,
with the same GitHub sign-in and the same publish-to-live loop 02-01 already proved end to end.

The settings singleton is the highest-risk item in the whole phase, and it fails *silently*:
`src/content/settings.json` wraps its fields under a `main` key because Astro's `file()` loader
treats a JSON file's top-level keys as entry ids, but a naive Sveltia file-collection writes
fields flat at the JSON root and does not recreate that wrapper. The CMS save appears to
succeed; the next build is what breaks (RESEARCH Pitfall 1). This plan writes the documented
fix — every settings field nested inside one object widget named literally `main` — and then
proves the build-side backstop actually fires by feeding the build a deliberately flat
settings file and requiring it to fail.

Two edge cases the CMS makes reachable get closed here rather than left to be discovered by the
assistant: clearing the optional Facebook URL currently writes a value the schema's URL
validator rejects, which would break the build on a change the settings form explicitly invites;
and a Learn post with no cover image must render no image slot at all.

Purpose: ADMIN-04 and ADMIN-05 are the two requirements that turn "the assistant can update one
listing" into "the assistant runs the site's content."
Output: the blog and settings collections in `public/admin/config.yml`, a widened settings
schema committed alongside it, and a `cms-collections-complete` check that proves all three
collections match the schema and that the failure modes above are closed.
</objective>

<assumption_delta_decision>
**Family:** `optional` — the scan flagged "optional cover image" on Learn posts (ADMIN-04).

**Decision: no-change.** `coverImage` stays optional rather than being promoted to required or
gaining a companion presence flag alongside it. Phase 1 already guards every read site with a
truthiness check, which makes an absent key and an empty string behave identically — no image
slot is rendered in either case. Promoting the field would force the assistant to find a cover
photo for every post; adding a separate flag alongside would introduce a second source of truth
for a question the value already answers. Task 2's round trip 3 converts this from an assumption
into a proven behavior rather than leaving it to be discovered.
